## 2. 核心设计目标达成度深度评估

### 2.1 架构纯度与信任模型：摆脱历史包袱，专注基础设施定位
- **设计初衷**：
  BSOS 的信任模型限定于受信任、规模受限的内部协同环境（Dunbar 数规模，~100–150 节点），系统不存储第三方数据，坚决剔除用于应对恶意对抗的在线复杂鉴权、逻辑墓碑与 GC 垃圾回收机制；同时明确存储层与客户端坚决不做分块（Chunking）与清单（Manifest），只做纯粹的 `one fid per object` 裸字节流基础设施。
- **达成度评估：100% 达成**
  - 服务端与客户端保持极致精简，去除了所有 HTTP 代理层与复杂的租户抽象；
  - 范围边界得到严格贯彻，`pkg/client` 与 `cmd/bsos` 严格维持“原始字节进、原始字节出”的基础设施定位；
  - 存储生命周期明确为“配置、写满、下线、重建”的物理生命周期，彻底消除了逻辑墓碑带来的膨胀与悬空隐患。

### 2.2 写入路径根本变革：零内存全量缓冲与两阶段并发模型（§3.3）
- **设计初衷**：
  NBSS 需要在内存中完整缓冲大对象才能计算哈希寻址，且持有整盘大锁，无法适应网络流式写入。BSOS 的核心突破是：**客户端计算并声明 FID，服务端信任并直写裸盘；通过全池 FID 网关与磁盘槽位预留两阶段模型，在不持有长锁的前提下实现高并发流式写入**。
- **达成度评估：100% 达成**
  - **流式 Direct I/O**：客户端首帧发送元数据，后续按 1MB chunk 持续流式推送，服务端直接向磁盘槽位写入，单机内存消耗由“与对象大小成正比”降低为常量级缓冲；
  - **全池并发原子性**：全池 FID 网关（Step 0）在多盘竞态下严格拦截普通写入与别名写入并发冲突；经受住了 64 路本地并发及跨公网 8 路并发的压力测试，无一例数据错位或静默丢失；
  - **超时防御**：30 秒停滞超时与 2 秒扇出超时机制均有自动化测试兜底，客户端异常断流可秒级释放全局预留资源。

### 2.3 存储介质与拓扑演进：SSD 适应性与多盘分层（§3.11, §3.12）
- **设计初衷**：
  摒弃针对机械硬盘寻道优化的“电梯升降机优先队列”，改用面向现代固态介质的“有界并发调度器（Bounded Concurrency Dispatcher）”；同时引入 zram 快速层偏好与冷启动快照持久化机制。
- **达成度评估：100% 达成**
  - **有界调度**：`write_dispatch_concurrency`（默认 64）在面对公网突发并发流时平稳调度，资源占用受限；
  - **分层路由精准**：$< 256\text{KB}$ 小文件稳定命中 zram 内存盘，大文件自动路由至物理持久盘；
  - **物理冷启动与故障自愈**：在 VPS 宿主机上通过 sysfs 彻底 reset zram 设备后，服务冷启动能够自动探测、还原快照、校验并重新上线，数据读回及 SHA-256 100% 吻合。

### 2.4 空间与可靠性保障：强制连续 Trim 碎片整理与 Bonnie 评估（§3.8, §4）
- **设计初衷**：
  裸盘槽位寻址天然存在外部碎片。BSOS 规定 Trim 后台碎片整理**持续强制运行、无禁用开关**，将小对象打包进容器并写入打包表锚点；同时通过 `Bonnie` 评估存储池当前单对象最大可靠放置容量。
- **达成度评估：100% 达成**
  - **Trim 强制性与鲁棒性**：后台调度器平稳触发，105 个分散小对象成功压实进打包容器；在 6 处关键故障点注入断电崩溃测试，冷启动索引重放后数据无一损毁；
  - **别名与容器免疫**：Trim 算法严格识别并排除了跳转别名指示项、别名物理目标以及打包表本身；
  - **Bonnie 科学指引**：在包含 384MB 物理盘与 320MB zram 的真实测试集群中，`Bonnie` 稳定输出 `ch_d_pow2: 24 ~ 26`（对应 16MB ~ 64MB），为上层应用规划写入提供了确定性依据。

### 2.5 寻址冲突与客户端驱动：一跳别名跳转协议（§3.4, CLIENT_SPEC）
- **设计初衷**：
  服务端不承担复杂的自动重试循环，将策略权交由客户端：物理槽位碰撞时，客户端通过 `jumpCode 1..255` 附加盐字节并计算新哈希，利用服务端原语 `alias_for -> targetFID` 注册一跳别名。
- **达成度评估：100% 达成**
  - **同盘物理共置**：指示条目与真实目标数据严格绑定在同一物理磁盘的相邻索引流中；
  - **透明无感知读取**：通过原始 FID 读取自动去除末尾追加的 1 字节跳转后缀，返回与初始写入完全一致的逻辑内容；
  - **非法状态拦截**：防覆盖已有对象、防自别名、防链式别名（`A -> B -> C`）全部被全池网关在 Step 0 阶段以 `AlreadyExists` / `InvalidArgument` 拦截；
  - **客户端自动跳转**：`pkg/client` 与 `bsos put` 在遇到槽位冲突时平滑探测并完成别名落盘，用户完全无需手动干预。

### 2.6 运维工程化与端到端交付（M7 - M9）
- **设计初衷**：
  提供符合 UNIX 哲学与标准基础设施运维规范的配置体系（TOML）、完备的 SDK 与易于集成的 CLI 工具。
- **达成度评估：100% 达成**
  - **生产级配置**：`bsosd.toml` 支持 `ParseSize`（支持 MB/GB 语义解析），支持参数边界严格校验，支持命令行参数显式优先覆盖；
  - **优雅平滑停机**：捕获系统 `SIGTERM` 信号，调用 `GracefulStop` 排水在途请求并原子持久化索引流，退出码为 0，与 systemd 服务管理器完美契合；
  - **生态工具落地**：本机 `bsos put` / `bsos get` 不仅支持标准参数操作与范围分片拉取，还支持原生 Unix 管道（`echo "..." | bsos put - | bsos get <fid>`）。

## 5. 架构边界纪律总结

BSOS 严格恪守最初的设计约定：
1. **No chunking / No manifest**：不属于单对象基础设施的职责，坚决不越俎代庖，彻底留给上层应用。
2. **No DELETE / No GC**：杜绝在线逻辑删除引起的元数据膨胀与随机碎片，存储池以物理盘为单位进行全生命周期轮替。
3. **No Auth / No Multi-tenancy**：专精受信内部集群基础设施，杜绝过度工程。

**BSOS 项目已圆满达成所有设计目的。其核心在理论上逻辑自治、在物理上极致精炼、在工程上经过了多层真实硬件与网络环境的严苛洗礼，已经完全具备作为下一代新型异构系统底层对象存储基石的能力。**
